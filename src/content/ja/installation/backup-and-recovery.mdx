# バックアップとリカバリ

QueryPie ACP のインストール環境で発生する障害やデータ損失に備え、システム全体をバックアップおよびリカバリする手順について説明します。

### 概要

QueryPie ACP は、一般的なステートフル Web アプリケーションと同様の特性を持っています。
バックアップとリカバリは、一般的な Web アプリケーションのバックアップおよびリカバリ手順と同等とみなすことができます。

QueryPie ACP はコンテナで実行され、主要な状態情報を MySQL データベースに保存します。
そのため、システムをリカバリするには、QueryPie が使用するデータベースとコンテナの実行に必要な設定情報をあわせてバックアップする必要があります。

システムの設定や構成によっては、連携する外部システムもバックアップおよびリカバリする必要があります。
特に、Secret Store として HashiCorp Vault や AWS Secrets Manager などの外部システムを使用している場合は、リカバリ後も Secret Store にアクセスできる必要があります。

### バックアップとリカバリの対象

QueryPie ACP を運用するシステムの障害に備えてリカバリを実行するには、次の対象をバックアップします。

#### QueryPie ACP 用の MySQL Database

QueryPie ACP は、ユーザーアカウント、アクセス対象の Database や Server などの資産情報、対象システムへのアクセスに必要な秘密情報、アクセス制御ポリシー、およびアクセスログを MySQL Database に保存します。
これらのデータは 3 つの論理的な Database に分かれており、それぞれの役割は次のとおりです。

* querypie
    * アクセス制御の対象とポリシー情報を保存します。このデータベースは QueryPie Meta DB と呼ばれます。ユーザーアカウント、アクセス対象の資産、対象システムへのアクセスに必要な秘密情報、アクセス制御ポリシーなど、ACP の運用に必要なデータの大部分がこのデータベースに保存されます。
* querypie_snapshot
    * ユーザーが対象システムに接続して SQL Query を実行した記録や、システムにアクセスして行った操作の記録を一時的に保存します。接続セッションが有効な間に使用され、セッションが終了すると querypie_log に移行されます。
* querypie_log
    * 監査記録を保存します。ユーザーが Database や Server などの資産にアクセスした記録と、ユーザーの操作履歴が記録されます。

監査記録を保持する場合は、3 つの Database をすべてバックアップして保管します。
監査記録を保持せず、障害発生時にアクセス制御機能を迅速に復旧することを目的とする場合は、`querypie` データベースのみをバックアップして保管します。
データベースのバックアップには、一般的な MySQL Database のバックアップおよびリカバリツールを使用できます。

#### コンテナの実行に必要な情報

QueryPie ACP コンテナを正常にリカバリするには、コンテナの実行に使用する環境変数とマウントファイルをあわせてバックアップする必要があります。
環境変数の詳細については、[コンテナ環境変数](container-environment-variables)を参照してください。

次の情報を含む、実際の運用環境のコンテナ設定全体を保管します。

* データベースと Redis の接続情報
* KEY_ENCRYPTION_KEY
* TLS 証明書と Private Key
* 外部システムの接続情報
* コンテナにマウントした証明書と設定ファイル
* QueryPie コンテナイメージのバージョン

特に、`KEY_ENCRYPTION_KEY` はバックアップ時の値をそのまま保管する必要があります。
この値が失われたり、異なる値でリカバリされたりすると、データベースに暗号化して保存された Connection パスワードや SSH Key などの秘密情報を使用できません。

環境変数と証明書にはパスワードや Private Key が含まれる場合があるため、暗号化された保存先に保管し、アクセス権限を制限してください。

AGENT_SECRET と REDIS_PASSWORD は、リカバリ中に変更できます。

Custom JDBC Driver、TLS 証明書、DAC_SKIP_SQL_COMMAND_RULE_FILE（`skip_command_config.json`）などのファイルを使用している場合は、これらもバックアップしてリカバリする必要があります。

#### Secret Store に保存される情報

QueryPie ACP に組み込まれた Secret Store ではなく外部の Secret Store を使用する場合は、Secret Store に保存された情報を失わず、継続してアクセスできるようにする必要があります。[Secret Store 連携](../administrator-manual/general/system/integrations/integrating-with-secret-store)の説明に従って HashiCorp Vault、Microsoft Active Directory、AWS Secrets Manager などに秘密情報を保存する場合は、対象システムに継続してアクセスできるか、接続情報を安全に保管してリカバリ後に接続できるかを事前に確認することを推奨します。

#### インフラストラクチャ構成

ACP の実行および運用に必要なインフラストラクチャ構成情報をバックアップし、リカバリできる必要があります。
VM 上で Compose を使用して実行するか、Kubernetes 環境で実行するかなど、インフラストラクチャ構成によってバックアップおよびリカバリが必要な情報は異なります。

[システムアーキテクチャとネットワークアクセス制御](system-architecture-and-network-access-control)で説明している Application Load Balancer、Network Load Balancer の構成、およびアクセス許可設定をバックアップする必要があります。
TLS 証明書を使用する場合は、証明書を復元する手順を準備してください。

#### バックアップおよびリカバリが不要な情報

QueryPie ACP の応答速度を向上させ、複数の Container の円滑な動作と一時的なデータ共有に使用される Redis のデータは、バックアップおよびリカバリの対象ではありません。

#### バックアップ範囲の概要

QueryPie ACP をリカバリするには、データベースとコンテナ実行設定をあわせてバックアップする必要があります。
データベースごとのバックアップ範囲は次のとおりです。

| バックアップ対象     | バックアップ範囲             | リカバリ目的                                               |
| -------------------- | ---------------------------- | ---------------------------------------------------------- |
| `querypie`           | スキーマとデータ             | アカウント、資産、秘密情報、アクセス制御ポリシー、システム設定 |
| `querypie_log`       | スキーマとデータ             | アクセスログ、実行ログ、その他の監査記録                   |
| `querypie_snapshot`  | スキーマと DDL               | リカバリ後に新しいセッションを処理するための DB 構造       |
| コンテナ実行設定     | すべての設定                 | QueryPie サービスの再起動                                  |
| `KEY_ENCRYPTION_KEY` | 元の値                       | 暗号化された秘密情報の復号                                 |
| 外部 Secret Store    | お客様の運用ポリシーに従ったバックアップ | リカバリした QueryPie が既存の Secret にアクセスできることの保証 |

`querypie_snapshot` のデータはアクティブなセッションに依存します。
サーバープロセスが再起動するかコンテナが置き換えられると、既存のセッションは無効になるため、このデータをリカバリしてもセッションは復元されません。
そのため、スキーマと DDL のみをバックアップし、テーブルデータをバックアップする必要はありません。

### バックアップ手順

QueryPie ACP のデータベースと実行設定は、同じ時点で取得した 1 つのバックアップセットとして管理することを推奨します。

1. 運用中の QueryPie コンテナイメージのバージョンと実行方法を確認します。
2. QueryPie が使用する `querypie`、`querypie_snapshot`、`querypie_log` データベース、およびコンテナの環境変数、証明書、マウントファイルの場所を確認します。
3. 外部 Secret Store とインフラストラクチャ構成のバックアップ状態を確認します。
4. 可能な場合は、QueryPie への新規リクエストを遮断するかコンテナを停止して、一貫したバックアップ時点を確保します。サービスを停止できない場合は、MySQL が提供する一貫性のあるオンラインバックアップ、またはマネージドデータベースのスナップショット機能を使用します。
5. バックアップ範囲で定義した `querypie`、`querypie_snapshot`、`querypie_log` データベースを、同じバックアップ処理または同じバックアップサイクルでバックアップします。
6. コンテナの環境変数、証明書、Custom JDBC Driver、およびその他のマウントファイルをバックアップします。
7. 外部 Secret Store とインフラストラクチャ構成情報を、お客様の運用ポリシーに従ってバックアップします。
8. バックアップが完了したことを確認し、バックアップファイルの整合性を検証します。
9. バックアップ日時と QueryPie コンテナイメージのバージョンを記録し、バックアップファイルを運用システムとは別の保存先に保管します。

#### mysqldump を使用したバックアップ例

次の例では、QueryPie ACP が使用する 3 つのデータベースを 1 つの SQL ファイルにバックアップします。
山括弧で示した値は、実際の MySQL 接続情報に置き換えてください。
```bash
mysqldump \
  --host="<MYSQL_HOST>" \
  --port="<MYSQL_PORT>" \
  --user="<MYSQL_USER>" \
  --password \
  --single-transaction \
  --hex-blob \
  --databases querypie querypie_snapshot querypie_log \
  > "querypie-backup-$(date +%Y%m%d-%H%M%S).sql"
```

`--password` オプションを使用すると、コマンド実行後にパスワード入力プロンプトが表示されます。
パスワードがシェル履歴やプロセスリストに露出する可能性があるため、コマンドラインにパスワードを直接入力しないでください。

`--single-transaction` は、トランザクションをサポートするテーブルを一貫した時点でバックアップするために使用します。
バックアップ中はスキーマ変更を実行しないことを推奨します。

バックアップアカウントには、3 つのデータベースを参照し、スキーマをダンプするために必要な権限が必要です。
コマンドの終了ステータスと生成されたファイルのサイズを確認し、秘密情報と監査ログを含む SQL ファイルは機密情報として安全に保管してください。

### リカバリ手順

1. バックアップ時と同じ QueryPie コンテナイメージのバージョンと実行環境を準備します。
2. MySQL と Redis を準備し、必要なネットワークアクセスを設定します。既存の Redis データはリカバリしません。
3. データベースのリカバリが完了するまで QueryPie コンテナを起動しないでください。
4. 同じバックアップセットから `querypie`、`querypie_snapshot`、`querypie_log` データベースをリカバリします。
5. コンテナの環境変数、証明書、Custom JDBC Driver、およびその他のマウントファイルをリカバリします。
6. `KEY_ENCRYPTION_KEY` には、バックアップ時と同じ値を必ず設定します。
7. 外部 Secret Store を使用している場合は、リカバリした環境から対象システムにアクセスできることを確認します。
8. Load Balancer、ファイアウォール、アクセス許可設定などのインフラストラクチャ構成をリカバリします。
9. データベース接続情報とリカバリ状態を確認した後、QueryPie コンテナを起動します。
10. QueryPie の起動状態とアプリケーションログを確認します。

サーバープロセスが再起動するかコンテナが置き換えられると、障害前に存在していたユーザーセッションは復元されません。
ユーザーは再度ログインし、対象システムに再接続する必要があります。

#### mysql CLI を使用したリカバリ例

次の例では、前述の `mysqldump` コマンドで作成した SQL ファイルを MySQL にリカバリします。
リカバリを開始する前に QueryPie コンテナが停止していることを確認し、山括弧で示した値とバックアップファイル名を実際の環境に合わせて変更してください。
```bash
mysql \
  --host="<MYSQL_HOST>" \
  --port="<MYSQL_PORT>" \
  --user="<MYSQL_USER>" \
  --password \
  < "querypie-backup-YYYYMMDD-HHMMSS.sql"
```

`--password` オプションを使用すると、コマンド実行後にパスワード入力プロンプトが表示されます。
パスワードがシェル履歴やプロセスリストに露出する可能性があるため、コマンドラインにパスワードを直接入力しないでください。

バックアップファイルは `--databases` オプションを使用して作成されているため、`querypie`、`querypie_snapshot`、`querypie_log` データベースの選択情報が含まれています。
リカバリアカウントには、データベースとスキーマを作成し、データを復元するために必要な権限が必要です。

コマンドの終了ステータスを確認し、エラーがない場合にのみ QueryPie コンテナを起動してください。
既存のデータベースにリカバリする場合は、事前に現在のデータを別途バックアップし、別の環境でリカバリ手順を検証してください。

### リカバリ後の確認

リカバリが完了したら、次の項目を確認します。

* QueryPie コンテナが正常に起動すること
* 管理者がログインできること
* ユーザーとグループが正常に表示されること
* アクセス対象の Database と Server が正常に表示されること
* ロール、権限、アクセス制御ポリシーが正常に表示されること
* 保存された Connection 情報を使用して対象システムに接続できること
* 既存のアクセスログ、実行ログ、監査ログの詳細を参照できること
* 新しいアクセスと操作が監査ログに正常に記録されること
* 外部 Secret Store を使用している場合、正常にアクセスできること
* Load Balancer とネットワークアクセス経路が正常に動作すること
* アプリケーションログにデータベース接続または初期化のエラーがないこと

### 注意事項

* データベースのバックアップには、MySQL が提供する公式バックアップツールまたはマネージドデータベースサービスのバックアップ機能を使用してください。実行中の MySQL データファイルを通常のファイルコピーでバックアップしないでください。
* `querypie`、`querypie_snapshot`、`querypie_log` は 1 つのバックアップセットとして管理し、リカバリ時も同じセットを使用してください。
* `KEY_ENCRYPTION_KEY` はバックアップ時と同じ値を使用してください。異なる値を使用すると、暗号化された秘密情報を正常に復号できません。
* データベースのリカバリが完了するまで QueryPie コンテナを起動しないでください。
* 障害前に開かれていたユーザーセッションは復元されません。
* バックアップファイルと設定情報は運用システムとは別の保存先に保管し、アクセス権限を制限してください。
* バックアップが成功しただけでは、リカバリできることを保証できません。別の環境でリカバリ手順を定期的に検証することを推奨します。
* バックアップ時と異なる QueryPie バージョンでリカバリとアップグレードを同時に実行しないことを推奨します。まずバックアップ時のバージョンでリカバリし、その後、別のアップグレード手順を実行してください。
